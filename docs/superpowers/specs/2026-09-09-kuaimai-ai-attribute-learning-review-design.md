# 快麦多平台 AI 属性学习与运营审核设计

日期：2026-09-09
状态：已完成需求与交互确认，待实施计划

## 1. 背景

当前快麦一键铺货以 Python、Playwright、平台接口数据和页面 DOM 为核心，Excel 为商品属性的主要输入。各平台存在大量公共字段，也存在会随平台、叶子类目、款式和当前页面候选变化的动态字段。

本设计在现有自动化上增加一套“结构化识图 + 当前候选约束 + 历史规则/案例 + 人工审核”的决策层。初期继续使用 Excel 辅助建立可信样本；长期目标是不再要求运营填写 Excel 属性，由系统根据商品图片、文字证据、当前平台候选和累积规则自动完成大部分字段，仅把真正无法确定的字段交给运营审核。

## 2. 目标

1. 提取跨平台公共字段，避免同一商品被每个平台重复解释。
2. 对品类、款式相关字段动态判断，不把“裤长、版型、厚薄”等值写死在类目中。
3. 每个商品只进行一次多图视觉分析，结果供所有平台复用。
4. AI 只能从当前页面/API 返回的合法候选中选择，不生成页面不存在的属性值。
5. 高可信结果自动填写；低可信、冲突或新品类字段进入网页审核中心。
6. 审核完成后从卡住的平台恢复，不重跑基础资料和已完成平台。
7. 保存后必须回读，只有已验证结果才能进入学习样本。
8. 使用 Cloudflare 提供轻量审核网页和中心数据服务，同时保留本地脚本、浏览器会话及离线能力。

## 3. 非目标

1. 不把 Playwright、Chrome 登录配置或快麦浏览器自动化迁移到 Cloudflare。
2. 不把 AI 输出直接当成平台值，也不允许 AI 绕过候选约束或保存回读门禁。
3. 不从无法证明最终保存成功的旧日志中学习“正确答案”。
4. 第一版不追求无人值守覆盖全部新品类；新品类先发现、审核和积累。
5. 审核网页不直接控制铺货发布，只提交属性决策并通知本地执行器续跑。

## 4. 总体架构

```text
商品图片 / Excel / 当前快麦页面
              │
              ▼
本地 Python 执行器
├─ 商品指纹与图片哈希
├─ 页面接口 JSON + DOM 双重发现
├─ 平台填写、保存、回读
├─ 检查点与幂等控制
└─ 本地 SQLite 缓存 / 待同步队列
              │ HTTPS + request_id
              ▼
Cloudflare Worker API
├─ 决策编排与模型适配器
├─ 规则 / 相似案例检索
├─ 审核任务 API
└─ 用户、权限和同步接口
       │                 │
       ▼                 ▼
      D1                R2
结构化事实、规则、      临时原图、
审核、检查点、回读      学习缩略图
       │
       ▼
运营审核网页
确认 / 改选 / 跳过 / 查看依据
```

### 4.1 部署边界

- 本地机器负责 Chrome、Playwright、Excel、图片预处理和所有快麦页面操作。
- Cloudflare 负责审核网页、HTTP API、D1、R2 和在线模型调用编排。
- 第一版不要求在当前项目中引入 FastAPI；本地 Python 通过 HTTP 客户端调用 Worker API。
- 如果后续需要 FastAPI，可在确认 Python Workers 运行时和依赖兼容后迁移轻量 API；浏览器自动化和依赖本机环境的代码仍留在本地。

## 5. 数据来源与可信等级

从高到低使用以下数据来源：

1. 当前商品的人工覆盖值。
2. 商品图片中的明确视觉证据，以及标题、Excel、OCR 中的明确文字证据。
3. 已成熟的条件规则。
4. 与当前商品条件相似、且保存回读成功的历史案例。
5. 在线模型在当前合法候选范围内的受限判断。

材料比例、功能性宣称等无法仅凭图片可靠判断的字段，必须有 Excel、标题、OCR 或其他文字证据；没有证据时进入审核，不做视觉猜测。

## 6. 数据模型

D1 是中心权威数据库，本地 SQLite 只是缓存、离线待同步队列和本机恢复索引。

### 6.1 商品和证据

- `products`：商品 ID、款号、标题、品牌、叶子品类、商品版本哈希。
- `assets`：图片哈希、R2 对象键、用途、尺寸、保留期限、商品版本。
- `visual_facts`：一次多图分析得到的结构化视觉事实，例如长度位置、轮廓、颜色集合、图间一致性。
- `text_facts`：Excel、标题、OCR 和其他文字证据的标准化结果。
- `fact_evidence`：事实对应的图片、区域、文字来源和冲突标记。

### 6.2 平台结构

- `canonical_fields`：跨平台标准字段，如 `pants_length`、`thickness`、`fit`。
- `platform_fields`：平台字段 ID、显示名称、所属类目、输入类型及对应标准字段。
- `option_snapshots`：某次打开页面时平台实际返回的候选值、`value_id`、文本和顺序。
- `schema_versions`：平台、叶子类目、字段集合和候选集合的版本指纹。

### 6.3 决策和学习

- `attribute_decisions`：建议值、最终值、来源、证据、决策状态和系统可信等级。
- `conditional_rules`：平台、叶子类目、标准字段、条件签名、目标值、连续确认次数、接受率和状态。
- `review_actions`：审核人、建议值、最终值、修改原因、时间及对应候选快照。
- `persisted_readbacks`：保存后从接口 JSON 或页面回读得到的实际值及验证结果。

### 6.4 运行恢复

- `run_checkpoints`：任务 ID、商品版本、图片版本、运行模式、当前平台索引和状态。
- `stage_results`：基础资料及各平台的开始、填写、保存、回读结果。
- `sync_outbox`：本地待上传事件、幂等键、重试次数和最后错误。

### 6.5 用户和权限

- `users`：用户名、密码哈希、角色、状态。
- `sessions`：短期登录会话、过期时间和撤销状态。
- 角色只设两级：`admin` 和 `operator`。
- 运营可处理审核；管理员可管理用户、规则、任务锁和数据删除。

## 7. 商品级视觉分析

### 7.1 一次分析，多平台复用

系统按“商品版本哈希 + 图片集合哈希”缓存视觉分析结果。同一商品在一次全平台流程中只做一次主要识图，不为每个平台和每个字段重复调用模型。

视觉输出必须是结构化 JSON，而不是自然语言结论，例如：

```json
{
  "garment_type": "pants",
  "visible_colors": ["army_green"],
  "length_landmark": "ankle",
  "silhouette": "straight",
  "thickness_evidence": "insufficient",
  "image_consistency": {
    "length_landmark": "4/5",
    "visible_colors": "5/5"
  },
  "evidence_asset_ids": ["asset_1", "asset_3", "asset_4", "asset_5"]
}
```

模型输出只记录可见事实；最终平台属性由后续决策器根据事实、规则和当前候选确定。

### 7.2 性能策略

- 能在打开快麦前完成的商品级识图优先并行准备。
- 图片哈希命中时直接复用结果。
- 只有证据冲突、候选难映射或新品类时，才执行第二次受限判断。
- 首次商品识图预计约 5–15 秒；必要的第二次判断预计再增加约 3–10 秒，具体取决于模型和网络，不作为 SLA 承诺。

## 8. 动态属性决策

### 8.1 类目不是固定答案

叶子类目只用于限制字段和候选空间，不直接决定属性值。例如“男士休闲裤”同时允许短裤、九分裤和长裤；每个商品仍要根据自己的图片、文字证据和历史条件判断。

### 8.2 决策顺序

对每个平台字段按以下顺序处理：

1. 获取当前页面/API 的字段结构和候选 `value_id`。
2. 映射到标准字段；无法映射时创建“字段映射审核”。
3. 查找当前商品人工覆盖值。
4. 合并视觉事实和文字事实，检测冲突与缺失。
5. 查询相同条件的成熟规则和相似成功案例。
6. 让模型仅在当前候选中选择，并返回候选 ID、证据 ID 和理由代码。
7. 通过系统可信门禁则自动填写，否则创建审核任务。

### 8.3 可信门禁

不能采用模型自报的“95% 可信度”。系统可信等级由以下条件共同决定：

- 必需证据是否完整。
- 多张图片是否一致。
- 文字与视觉证据是否冲突。
- 当前候选是否唯一且仍然存在。
- 相同条件规则是否成熟。
- 该字段/类目近期自动建议的实际接受率。

任一硬性条件失败时进入 `review_required`。第一版采用保守策略，不为所有字段设置一个通用分数阈值。

### 8.4 规则升级与降级

规则作用范围是：

```text
平台 + 叶子类目 + 标准字段 + 条件签名
```

同一品类不同款式通过条件签名区分，例如裤长规则可包含视觉落点、商品类型和文字证据，而不是只写“休闲裤 = 长裤”。

规则升级为自动规则必须同时满足：

1. 相同条件下至少连续 3 次人工确认。
2. 近期建议接受率不低于 95%。
3. 当前页面仍存在完全对应的候选 `value_id`。
4. 没有新的冲突证据或平台结构变化。

人工纠正、候选变化或结构版本变化会使规则立即降级，重新进入观察或审核状态。

### 8.5 新品类兼容

新品类首次出现时：

1. 通过接口 JSON 获取字段和候选，以 DOM 回读显示名称和当前状态进行校验。
2. 已知字段自动映射到标准字段。
3. 未知字段进入字段映射审核，不猜测语义。
4. 完成的人工确认按正常样本进入规则统计。
5. 同条件达到 3 次连续确认且接受率不低于 95% 后，才允许自动填写。

## 9. 页面发现、填写与校验

- 接口 JSON 是结构和候选的首选来源。
- DOM 用于实际点击、输入，以及校验页面展示状态。
- 下拉候选可匹配时必须选择合法候选；无下拉且页面允许自由输入时才使用输入模式。
- 保存前验证必填字段、候选 ID、图片数量和动态区块已完成加载。
- 保存后优先读取接口 JSON；接口不能覆盖的字段再用 DOM 回读。
- 回读结果必须与预期标准化值一致，才能标记平台阶段完成并进入学习样本。

## 10. 运营审核中心

### 10.1 页面目标

审核页采用已确认的 Apple 风格单任务决策卡：产品优先、框线克制、清晰字体层级，一次只处理一个判断。

主页面只展示：

- 商品大图和基础识别信息。
- 当前平台与字段名称。
- AI 建议值。
- 当前页面合法候选值。
- “查看判断依据与相似商品”的渐进式详情。
- “暂时跳过”和“确认并继续”操作。

字段名称必须独立显示，不能只展示候选项。待审任务数量和下一任务只作为轻量进度提示，不使用超宽主从后台布局。

### 10.2 审核动作

- 确认建议：记录建议值为最终值。
- 改选候选：记录新的合法候选并要求选择纠正原因。
- 暂时跳过：保持任务待审核，不触发续跑。
- 管理员撤销：撤销未被续跑消费的审核；已保存的数据需新建纠正任务。

审核按钮只记录决策并通知本地执行器，不从网页直接点击快麦“保存”或“铺货”。

### 10.3 多人防冲突

- 同一任务同时只允许一位运营提交。
- 领取后默认锁定 10 分钟，持续操作时续租。
- 其他运营可以查看但不可提交。
- 管理员可强制释放失效锁。
- 所有提交使用任务版本号做乐观并发校验。

## 11. 中断、审核与续跑

### 11.1 检查点

每次全平台运行记录：

- `run_id` 和幂等键。
- 商品 ID、商品版本哈希、图片集合哈希。
- 运行模式及平台有序列表。
- 当前平台索引。
- 已完成平台的保存回读证据。
- 当前待审核字段及其候选快照。

### 11.2 中断流程

遇到 `review_required` 时：

1. 写入本地检查点和待同步事件。
2. 创建中心审核任务。
3. 安全退出当前商品编辑页。
4. 不保存未经确认的字段，不继续后续平台。

### 11.3 审核后恢复

1. 本地执行器获取已确认任务。
2. 校验商品版本、图片版本、运行模式和检查点。
3. 重新打开同一商品，并直接进入卡住的平台。
4. 重新获取当前字段和候选，不沿用旧 DOM。
5. 如果已确认值仍存在，幂等填写并保存。
6. 保存后回读成功，写入阶段结果。
7. 从下一平台继续运行；基础资料及之前已完成的平台不重跑。

如果商品、图片、执行模式或页面候选发生变化，旧审核结果失效并重新创建审核，不强行续跑。

## 12. 幂等与离线同步

### 12.1 幂等键

建议使用以下组合生成幂等键：

```text
run_id + product_version + platform + field_id + action_type
```

中心 API、D1 写入、本地 outbox 和恢复动作都必须识别该键。重复点击、超时重试和脚本重启不得产生重复审核任务或重复保存。

### 12.2 Cloudflare 不可用

- 本地先把事件写入 SQLite `sync_outbox`，再尝试上传。
- 网络失败不丢任务，按退避策略重试。
- 需要审核的运行保持暂停，不绕过中心审核继续填写。
- 已完成平台的本地检查点仍可恢复。
- 中心恢复后按幂等键补传，服务端返回已有结果时本地直接对账。

### 12.3 D1 与本地 SQLite 冲突

- D1 的已提交审核决策和回读记录是中心权威结果。
- 本地 SQLite 不覆盖更高版本的中心记录。
- 冲突按任务版本号和事件时间解决；无法自动合并时创建管理员异常任务。

## 13. 图片保留与安全

- 商品原图存入 R2，仅用于识图和人工审核，默认 30 天后自动删除。
- 经人工确认的学习案例长期保留压缩缩略图，用于展示相似案例。
- D1 长期保存结构化事实、最终值、审核记录和图片哈希，不保存高清原图。
- 管理员可按商品删除原图、缩略图和学习记录；删除后不得继续参与检索或规则统计。
- 快麦 Cookie、Chrome Profile、平台密码和浏览器登录状态只留在本地，不上传 D1/R2。
- 用户密码仅保存强密码哈希，不保存明文。
- 在线模型密钥使用 Cloudflare Secret，不写入仓库或数据库。
- R2 图片不公开访问，审核页通过短期授权地址读取。
- 操作日志记录任务、用户和结果，不记录密码、Cookie、Token 或完整模型密钥。

## 14. API 边界

第一版至少提供以下逻辑接口，具体路由名称在实施计划中确定：

- 创建/幂等更新商品和资产元数据。
- 提交视觉事实和文字事实。
- 提交平台字段、候选快照和结构版本。
- 请求字段决策。
- 创建、领取、续租、提交和跳过审核任务。
- 获取某本地执行器的待恢复任务。
- 上报阶段结果和保存回读。
- 查询规则、相似案例和审核历史。
- 管理员删除商品数据、释放任务锁和停用规则。

所有写接口必须携带幂等键和记录版本；所有恢复接口必须返回当前候选快照版本和商品版本。

## 15. 状态机

### 15.1 属性决策

```text
discovered
  ├─ auto_fill_ready ──> filled ──> saved ──> readback_verified
  └─ review_required ──> claimed ──> confirmed ──> resume_ready
                                             └─ invalidated ──> review_required
```

### 15.2 运行任务

```text
running ──> waiting_review ──> resume_pending ──> running
   │                                                   │
   ├─ failed                                           └─ completed
   └─ cancelled
```

只有 `readback_verified` 的阶段才算完成；提交了保存请求但未回读，不得继续后续平台。

## 16. 错误处理

- 页面接口失败：记录接口错误，尝试 DOM 只读发现；结构仍不完整则停止并审核。
- DOM 不一致：重新抓取接口 JSON 和 DOM 快照；不使用旧定位器盲点。
- 图片未加载：等待实际图片数量和稳定状态；超时后进入异常，不提前保存。
- 候选消失：使旧决策失效，重新决策或审核。
- 保存失败：保留当前平台检查点，不继续后续平台。
- 回读不一致：记录预期值与实际值，停止并创建异常任务。
- 在线模型失败：使用已成熟规则；规则不足时进入审核，不反复调用模型阻塞页面。
- Cloudflare 断网：写入本地 outbox 并暂停需要审核的任务。
- 本地进程重启：从最近一个已回读成功的平台之后恢复。

## 17. 验收标准

1. 高可信字段自动填写；低可信字段只创建审核任务，不擅自保存。
2. 人工确认后从卡住的平台恢复，基础资料和已完成平台不重跑。
3. 恢复时重新获取页面候选；候选变化时旧审核结果失效。
4. 保存后必须回读 JSON/页面状态；回读失败立即停止后续平台。
5. 重复点击、断网重试或脚本重启不会产生重复任务或重复保存。
6. 同条件连续人工确认至少 3 次且近期接受率不低于 95%，规则才升级为自动。
7. 新品类能自动发现字段和候选；无法确定的字段映射进入审核。
8. Cloudflare 暂时不可用时，本地 SQLite 保存待同步任务，恢复后自动补传。
9. 原图到期自动清理；管理员删除后的数据不再作为学习样本。
10. 用裤子、外套、双颜色商品和一个全新品类完成端到端验证。
11. 验证材料比例字段在无文字证据时不会被视觉模型猜填。
12. 验证多颜色商品的颜色分组和图片顺序不会因共享规则被错误覆盖。

## 18. 分阶段交付

### 阶段一：数据与检查点

- 建立本地 SQLite schema、outbox、商品/图片哈希和平台检查点。
- 把现有保存回读结果结构化。
- 接入平台字段和候选快照。

### 阶段二：中心服务与审核页

- 部署 Cloudflare Worker、D1、R2。
- 实现账号密码、管理员/运营角色和单任务锁。
- 上线已确认的单任务 Apple 风格审核页。
- 打通审核后从卡点平台续跑。

### 阶段三：识图与受限决策

- 接入一次多图结构化分析和缓存。
- 实现标准字段映射、候选约束、证据检查和 `review_required`。
- 从当前 Excel 和已验证历史结果导入种子样本。

### 阶段四：规则学习与新品类

- 实现条件签名、连续确认计数、接受率和规则升降级。
- 实现相似案例检索及新品类字段映射审核。
- 完成四类端到端验收并逐步扩大自动填写范围。

## 19. 实施原则

- 现有每个平台的稳定填写逻辑不一次性重写；新决策层通过明确接口逐步接入。
- 先让系统“不会填错且能恢复”，再提升自动化覆盖率。
- 所有学习样本都必须能追溯到证据、人工动作和保存回读结果。
- 所有自动规则都必须可查看、可降级、可停用和可删除。
